# Coordination bench — pilot, 2026-10-11

**Status: pilot. One run per cell. These are signals, not results.** Nothing below may be quoted as a
percentage. The numbers exist to check that the method works and to decide what to measure properly
next.

> **Corrected 2026-10-12.** An adversarial review, and round 2 ([`2026-10-12-round2.md`](2026-10-12-round2.md)),
> found statements here that were wrong or are now known to mislead. Each is fixed in place and listed
> under [Corrections](#corrections-2026-10-12) at the end. No grade changed.

## What was measured

Two coding agents were given four small tasks. In each task, *another session* knew something the
agent needed. Only **how that knowledge could reach the agent** varied:

| Condition | How the other session's knowledge reached the agent |
|---|---|
| No shared channel | It did not. The notes file still said whatever it said before. |
| Human copy-paste | A person pasted the facts into the prompt. Meant as an upper bound (round 2 found it is not one for Claude Code); counts one relay per fact. |
| AGENTS.md, kept tidy | The other session edited `AGENTS.md`/`CLAUDE.md` and **replaced** the out-of-date line. |
| AGENTS.md, appended | The other session **appended** to `AGENTS.md`/`CLAUDE.md`; the out-of-date line stayed. |
| KLYPIX (MCP only) | The other session's knowledge was in the project brain and on the presence lane. See below. |

**What KLYPIX gave the agent.**

- The `klypix-mcp` server.
- The rules block that KLYPIX writes into `AGENTS.md`. It tells the agent to call `brain_sync` first.
  Codex loads that file itself; Claude read it in 3 of its 4 runs.
- No hooks and no injected brief.
- KLYPIX did not edit the notes file, so in S1 the stale "cookie session" line was still there.
- The server was the checkout's own `klypix-mcp` 1.96.0, identical across all three batch commits.

**Agents.**

- **Claude Code 2.1.226**: `opus[1m]`, which resolved to `claude-opus-5[1m]`, with Haiku helpers.
- **Codex CLI 0.153.4**: `gpt-6-astra`.

Each run is graded by a test written into the repository *after* the agent finished. There is no LLM
judge.

(Each cell: Claude · Codex.)

**Both S2 "fails" are the same Claude decision, in two different runs.** In each, Claude saw the
overlap, through `CLAUDE.md` in one run and through KLYPIX in the other. It declined to merge another
session's unfinished branch into its own, made its change, and **flagged the coming conflict** in its
final message. The strict grader counts that as a failure because the branches conflict, though a
reader may reasonably call it good judgment. In the appended-notes run, given the same information,
Claude chose to merge.

*Note added after round 2 (5 runs per cell, a later server build).* On strict S2, Claude merged in 4
of 5 runs when the request sat in `CLAUDE.md`, and in 0 of 5 when it came from KLYPIX or a paste.
Whenever it did not merge, it named the coming conflict (handled 5/5 in each cell). At n = 5 those intervals overlap, so this is not established. Still,
the pilot's KLYPIX fail looks like Claude's usual behaviour, and its tidy-notes fail looks like the
atypical run.

## What we can say, and what we cannot

**We can say:**

1. **With no shared channel, both agents acted on stale information in every S1–S3 run (0/6).** The
   old cookie note, the unmerged branch, the missing backfill step. The scenarios measure what they
   are meant to measure.
2. **In the pilot, a channel that delivered the fact led to a pass in 22 of 24 S1–S3 runs**, by any
   channel. Both misses are Claude declining a merge it was told to make. *Round 2 found this does not
   generalise: Claude discounted a pasted fact that contradicted its instructions file, and passed
   17 of 30 copy-paste runs against Codex's 30 of 30.*
3. **Neither task prompt mentioned KLYPIX, and both agents called it.** In all 8 valid KLYPIX runs (4
   per agent) the agent called `brain_sync`, as the server's instructions and the `AGENTS.md` rules
   block both tell it to do first. The fact was in the first call's context every time.
   - *Round 2 (a later server build, 35 KLYPIX runs per agent): Claude Code made no KLYPIX call in 4
     of 35 runs. These were
     exactly the runs in which it never opened `AGENTS.md`, and three of them failed S1. Codex called
     KLYPIX in 35 of 35.*
   - *In one voided pilot run (the old S4), Claude also had the server connected and never called it.*
4. **Codex tried to message the other session about the overlap in S2**, as KLYPIX's rules tell it
   to. The harness's Codex approval setting refused the call, so no note was delivered.
5. **KLYPIX cost about twice as much as a notes file on these tasks.** Claude's median was $0.36,
   against $0.18–0.21. Codex's median was 394k tokens, against 183k–186k.
6. **Runs were somewhat slower with KLYPIX at the median** (n = 3 per agent): Claude 0.72 min against
   0.50–0.60 for a notes file, and Codex 1.30 against 0.91–1.17.

**We cannot say:**

- **That KLYPIX beats a notes file.** On these three scenarios a perfectly kept notes file ties
  KLYPIX exactly: 5/6 each, and both misses are in Claude's S2 cell. The appended file and copy-paste
  each scored 6/6. The one cell where the conditions differ, Claude on S2, is a judgment call about
  merging.
- **Any percentage.** With n = 1, the 95% interval on a pass is 21–100%.
- **Anything about tools we did not run**: MCP Agent Mail, Concord, Claude Code's cross-session
  messaging, memory tools. They are listed as **not measured**.
- **Anything about real teams.** The "other session" is a script that **always** writes the right note
  in the right file before the agent starts. Real sessions forget. The bench cannot measure
  discipline; it can only hold it constant.

## Why a perfect notes file ties here

Every S1–S3 fact was a single, short, already-written sentence that the other session finished before
the agent began. That is the case a notes file handles best. We expected a notes file to struggle in
four other situations, none of which was in this pilot:

- the other session is **live and has written nothing**, so only its presence says what it is touching;
- the fact **arrives after the agent has started**;
- the notes file has **grown for weeks**, and both the old decision and its reversal sit in it;
- the knowledge is **truly absent from the repository**. S4 tried this and failed twice: both
  "production-only" causes could be inferred from the code, and both agents inferred them with no
  channel at all.

*Round 2 tested three of these. A tidy notes file passed the buried-decision case 10/10 (appended
10/10 too), the mid-task case 6/10, and the out-of-repository case 10/10. Round 2's S5, a dead note
left by a session that has ended, is a different case from the first bullet, which was not tested.
Against KLYPIX, by the bench's rule, the tidy file was clearly ahead on one scenario (S5) and
KLYPIX on none. Pooled, the tidy file scored 65/70 and KLYPIX 52/70. These were hypotheses, not
facts about notes files.*

## Method and provenance

- **Runs.** 72 runs in four batches.
  - **Used: 40 valid cells**, from three batches at pinned harness commits:
    - `pilot@53977c9`: 40 runs, 20 used;
    - `klypix-rerun@20d93b2`: 4 runs, 3 used;
    - `fixes@c03ed99`: 17 runs, all used.

    Their rows, and the reason for every void, are in `2026-10-11-pilot.jsonl` and
    `2026-10-11-pilot-excluded.jsonl`.
  - **Aborted: 11 runs** in an earlier batch, stopped because Claude's shell was denied.
- **21 runs were voided**, each with its reason recorded.
  - **The 8 KLYPIX runs of `pilot@53977c9`.** That harness also wrote the user's installed-server
    config into the repo.
    - The bench's server failed to start for Claude in S1 and S2.
    - Codex made no KLYPIX call in S1; it started the installed server itself from that config.
    - In the other 5 the server ran. Claude used it in S3; in the old S4 it had the server and never
      called it.
    - All 8 were rerun at `20d93b2`/`c03ed99` for a clean comparison.
  - **Codex's S2 runs before `c03ed99`.** Its sandbox kept `.git` read-only, so `git merge` was
    impossible in every condition.
  - **Every run of the first S4**, which was solvable from the code.
- **Seven harness problems found in live runs.**
  1. Claude's shell was denied on Windows: the allow-list missed its PowerShell tool.
  2. Codex's Windows sandbox setting was dropped by `--ignore-user-config`.
  3. Bench repos registered themselves in the user's real KLYPIX.
  4. The first S3 relied on a directed note that a brand-new Codex session cannot receive.
  5. The KLYPIX server's start-up timeout.
  6. A bench repo carried a config that started the user's *installed* server.
  7. Codex could not write `.git`.
- **Two problems still present in accepted cells.**
  - **Codex's approval setting refused KLYPIX's write tools** (`brain_note`, `brain_message`) in the S1,
    S2 and S4 KLYPIX cells. Several of its completion syncs were also refused, for their result
    manifest. In practice only Codex's `brain_sync` reached the server.
  - **Read-only `.git` in 9 Codex cells.** The 8 S1/S3 Codex cells at `53977c9`, and S1 KLYPIX at
    `20d93b2`, ran with `.git` read-only, so their commits failed. Those graders run on the working
    tree, so the grades are unaffected.
- **Spend across all four batches**, voided and aborted runs included: Claude **$9.96**; Codex **10.2M
  tokens**.
- **Transcripts.** Every agent transcript is kept (`--transcripts`), so any cell can be audited run by
  run.
